# Marketing Assistant

Internal tool for finding relevant X posts, drafting replies, and generating
daily growth digests. Built around a product profile system — the first profile
is **Signal Shift**, a calm AI-powered market briefing tool for retail investors.

Digests are generated by **Mel**, the internal marketing assistant.

---

## Quick start — mock mode, no email

No API keys or configuration needed.

```bash
pip install -r requirements.txt
python run_mock.py
```

The digest is saved to `output/daily_digest_YYYY-MM-DD.md`.

## Real X mode — live post discovery

`run_x.py` fetches real recent X posts matching the Signal Shift profile,
scores them using keyword-based fit logic, and generates the digest.

**Safety:** Read-only. Nothing is posted, liked, followed, or replied to automatically.
Reply suggestions are for manual review only.

### Requirements

- An X Developer account with a project and app
- A Bearer token with **read-only** permissions (OAuth 2.0)

### Step 1 — Get an X Bearer token

1. Go to [developer.x.com](https://developer.x.com) and create a project + app
2. Under your app → **Keys and Tokens** → copy the **Bearer Token**
3. The Bearer token only needs read access — do not grant write permissions

### Step 2 — Add the token to your environment

**For local use**, add to your `.env` file:

```
X_BEARER_TOKEN=your_token_here
```

**For GitHub Actions**, add a repository secret named `X_BEARER_TOKEN`
(see GitHub Actions section below for the full secrets table).

### Step 3 — Configure your handles in the profile

Edit `profiles/signal_shift.yaml` and set your real handles:

```yaml
handles:
  founder: "@yourhandle"      # replace with real founder handle
  product: "@SignalShiftCo"   # replace with real product handle
```

The posting history check uses these handles to determine whether to skip
today's original posts.

### Step 4 — Run

```bash
python run_x.py
```

Mel fetches up to 10 recent posts from X, scores them, generates reply suggestions,
saves the digest, and (if `SEND_EMAIL=true`) sends the email.

### How fit scoring works in real mode

Mock mode uses hardcoded scores for 8 specific posts. Real mode uses keyword-based
scoring driven by `fit_keywords` in `profiles/signal_shift.yaml`:

| Tier | Logic |
|---|---|
| **Avoid** | Any avoid keyword present → hard stop, no engagement |
| **Weak fit** | Any weak keyword present → outweighs positive signals |
| **Strong fit** | 2+ strong keywords hit → high relevance |
| **Decent fit** | 1 strong or 1+ decent keyword → worth considering |
| **Weak fit** (fallback) | No matching keywords → assume misaligned |

Edit `fit_keywords` in the profile YAML to tune scoring for your product.

## Enable email delivery

Email is off by default (`SEND_EMAIL=false`). To turn it on:

### 1. Get a Resend account

Sign up at [resend.com](https://resend.com). The free tier allows 100 emails/day.

### 2. Create an API key

In the Resend dashboard → **API Keys** → create a new key with sending permission.

### 3. Verify a sending domain

In the Resend dashboard → **Domains** → add and verify your domain.

For initial testing, Resend provides a shared sandbox address:
`onboarding@resend.dev` — you can send from this without domain setup, but
delivery is limited to your own verified email address in Resend.

### 4. Create your .env file

```bash
cp .env.example .env
```

Then edit `.env`:

```
SEND_EMAIL=true
EMAIL_PROVIDER=resend
RESEND_API_KEY=re_your_key_here
EMAIL_FROM=Mel <mel@yourdomain.com>
EMAIL_TO=you@example.com
```

### 5. Run

```bash
python run_mock.py
```

Mel will generate the digest, save it locally, and send the email.

---

## How to test email safely

1. Set `EMAIL_TO` to your own email address — never a customer or public address.
2. Run once and check your inbox (check spam if it doesn't arrive).
3. Confirm delivery in the Resend dashboard at **resend.com/emails**.
4. The digest is always saved locally to `output/` even if email fails — nothing
   is lost if the send does not go through.

## What the digest contains

1. **Today's Best 3** — top posts worth replying to, filtered by fit and opportunity
2. **8 mock X posts** scored across three dimensions:
   - **Fit** — Strong / Decent / Weak / Avoid
   - **Visibility** — Strong / Decent / Low (raw engagement metrics)
   - **Opportunity** — High / Medium / Low / Poor (fit + timing + audience quality)
3. **Why it is or is not worth engaging** for each post
4. **3 reply options** (A/B/C) for every Strong or Decent fit post
5. **Suggested account** — Founder, @SignalShiftCo, Either, or Do not reply
6. **Media suggestion** per reply — No media / Optional GIF / Quote repost / etc.
7. **Original post drafts** — schedule-aware, with format and media guidance
8. **Posting history awareness** — skips posts if an account already posted today

## Email vs Markdown artifact

Mel produces two outputs every run:

| Output | What it contains | Where it goes |
|---|---|---|
| **HTML email** | Today's Best 3 — all reply options, media guidance, quick links | Sent via Resend if `SEND_EMAIL=true` |
| **Markdown artifact** | All 8 posts — full scoring detail, all reply options, original post drafts | Saved to `output/` and uploaded as a GitHub Actions artifact |

### What the HTML email includes per card

- Fit, visibility, and opportunity badges
- Engagement summary
- **Recommended reply** highlighted (the best option, copy-ready)
- **Other reply options** shown below so you can pick the right tone
- **Media guidance** — type, specific GIF idea or use-case, when to use it, when to skip it
- "Open post ↗" and "View profile" buttons

The email is designed for mobile: scan, pick a reply, open the post, done.
The Markdown artifact is the complete reference for every post in the run.

## Where digests are saved

```
output/daily_digest_YYYY-MM-DD.md
```

One file per day. Rerunning the same day overwrites the existing file.

The `output/` directory is listed in `.gitignore` — generated digest files are never committed to the repository. The directory is created automatically at runtime if it doesn't exist.

For saved runs, use the GitHub Actions artifact (uploaded every run regardless of whether email is enabled). Do not commit output files manually.

## GitHub Actions — automated digest and email

The workflow at `.github/workflows/mel_digest.yml` runs Mel on GitHub's
infrastructure. It can be triggered manually at any time, and optionally
scheduled for daily runs.

> **Security reminder:** Never put API keys in code, workflow files, or chat.
> Use GitHub Secrets exclusively. Nothing in this repo contains real credentials.

### Step 1 — Add GitHub Secrets

Go to your repository on GitHub:

**Settings → Secrets and variables → Actions → New repository secret**

Add each of these secrets:

| Secret name | Required for | Value to set |
|---|---|---|
| `SEND_EMAIL` | Email delivery | `true` to email the digest, `false` to skip email |
| `EMAIL_PROVIDER` | Email delivery | `resend` |
| `RESEND_API_KEY` | Email delivery | Your Resend API key (starts with `re_`) |
| `EMAIL_FROM` | Email delivery | e.g. `Mel <mel@yourdomain.com>` |
| `EMAIL_TO` | Email delivery | The address you want the digest sent to |
| `X_BEARER_TOKEN` | Real X mode only | Your X API v2 Bearer token (read-only) |

`X_BEARER_TOKEN` is only needed if you switch the workflow to use `run_x.py`.
The default workflow uses `run_mock.py` and does not require it.

You can set `SEND_EMAIL=false` first to test the workflow runs cleanly before
wiring up email.

### Step 2 — Run the workflow manually

From a browser or the GitHub mobile app:

1. Go to your repository
2. Tap the **Actions** tab
3. Select **Mel's Daily Digest** from the left sidebar
4. Tap **Run workflow** (top right of the workflow runs table)
5. Leave the branch as `main` and tap the green **Run workflow** button

The run will appear in the list within a few seconds. Tap it to watch the logs.

### Step 3 — Download the digest

Every run uploads the digest as a GitHub Actions artifact regardless of whether
email is enabled. To download it:

1. Open the completed workflow run
2. Scroll to the **Artifacts** section at the bottom
3. Download **mel-digest-\<run-id\>** — it contains the Markdown digest file

### Enabling scheduled daily runs

The workflow includes a daily schedule that is commented out by default.
To enable it, edit `.github/workflows/mel_digest.yml` and uncomment these lines:

```yaml
  # schedule:
  #   - cron: '0 8 * * 1-5'  # weekdays at 8am UTC
```

Change the cron expression to suit your timezone and preferred run time.
[crontab.guru](https://crontab.guru) is useful for checking cron syntax.
